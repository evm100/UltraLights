UltraLights Blueprint

A ground-up redesign of UltraLights: new ESP32-C6 hardware on a custom PCB, lean ESP-IDF 6.x firmware, a rebuilt server and broker, and a calm interface modeled on the room-and-slider style in research/. It covers what we're building, how the pieces fit, and what we're keeping from v5.

One device contractNodes, the OpenRGB bridge and future devices all describe themselves with the same capabilities.
Hardware does the dimmingLEDC fades replace the v5 software smoothing tasks.
Lean by constructionEach board profile compiles only the drivers it uses. Effects are data, not code.
Workers connect outThe 4080 machine builds firmware and runs AI jobs without exposing a single port.
Four rolesAdmin, Owner, Member and Guest, with guest access granted per room or device.
Matter later, on the serverNo Matter stack in firmware. A server-side bridge can be added if wanted.

01 · Scope

Goals and scope

UltraLights controls the lighting and simple switched loads in a handful of homes. Most people use it to turn rooms on and off and set brightness and warmth. Its owner (you) also needs to build, register, update and support every device from a web browser.

In scope

  • Outputs: PWM white, dual white (CCT), RGB, RGBW and RGB+CCT; addressable strips (ARGB); relays; solenoids.
  • Inputs: power monitoring on every board; motion sensors in a later phase.
  • One modular board, populated differently per install, with firmware built from matching modular components.
  • A room-first interface with a big brightness control, white and color tabs, scenes and schedules.
  • Homes with an Owner, Members and Guests who have limited access.
  • An admin panel that does everything the v5 CLI tools did: registration, profiles, builds, OTA, bring-up, health and certificates.
  • Low-friction problem reports that land in the admin panel.
  • The OpenRGB host as a bridged device.
  • Hooks so an AI worker can create scenes and schedules and, later, use room layout.

Out of scope (for now)

  • Matter or Thread in firmware. A server-side bridge is a later option.
  • ESP-NOW mesh and dual-chip gateway for larger venues. Same node hardware, later firmware.
  • A large built-in effect catalog. A small set of building blocks replaces it.
  • Software brightness smoothing on the node.
  • Cloud dependencies. Everything runs on your own machines.
  • Native mobile apps. The web UI is built phone-first and can be installed to the home screen.
02 · Architecture

System architecture

One machine is the hub. Everything else connects to it, never the other way round. Only the main VM accepts incoming connections. Devices, bridges and workers all dial out to it, so the build machine and home networks need no port forwarding.

Orange lines carry device traffic over MQTT. Blue lines are workers polling for jobs. The dashed line is the HTTPS firmware download during OTA. Live ARGB frames from a local PC are the one exception: they go straight across the home LAN (see Clips and streaming).

Machines and roles

Main VM hub, always on

Runs the reverse proxy, web app and API, scheduler, MQTT broker, database, device CA (intermediate key only) and artifact store. Everything persistent lives here and gets backed up together.

If this VM is down, lights keep their last state and wall switches still work. Remote control, schedules and the UI stop until it returns. The scheduler runs here rather than on nodes so that schedules have one source of truth.

Workstation (RTX 4080) workers, can be off

Hosts two workers that are the same kind of program: they authenticate to the API, claim a job, do it and upload the result. The build worker runs ESP-IDF 6.x in a pinned container and signs the images it produces. The AI worker runs local models on the GPU.

When the workstation is off, jobs wait in the queue and the admin panel shows the worker as offline. Nothing else is affected.

C6 nodes your PCB

Each node connects out to the broker with its own certificate. It keeps its last state in flash and restores it after a power cut, so a light that was on stays on without waiting for the server.

Bridge agents OpenRGB now, others later

A bridge is a small program that sits next to a foreign system and translates it into the device contract. The OpenRGB agent on your PC publishes one device per OpenRGB controller, with color and argb capabilities. The server and UI can't tell it apart from a C6 node.

A Matter bridge would be the same idea in reverse: it exposes UltraLights devices to Apple or Google Home.

03 · Device model

Device model

A device is one node or one bridged thing. It has one or more outputs, and each output lists its capabilities. The UI draws controls from capabilities alone: an output with level and cct gets the brightness slider and the white tab; an output with only onoff gets the ON/OFF pill. Adding a new device type never needs new UI code.

RGBW is worth it. RGB strips make a poor, tinted white. Six identical low-side MOSFET channels on the PCB cover every PWM row above, and with the optional flyback diode fitted, any of them can drive a relay or solenoid coil. Which channels form which output is a setting, not a different board (see Board and population). Solenoids differ from relays because many can't stay energized, so they get pulse rather than onoff. The firmware enforces a maximum on-time, and a hardware timeout on the PCB would make sure a crash can't leave a valve open.

04 · Hardware

Hardware and firmware

ESP32-C6 facts (verified)

  • Module: ESP32-C6-WROOM-1 (PCB antenna) or -1U (external). N8 or N16 flash. There is no WROVER variant.
  • No PSRAM. 512 KB HP SRAM and 16 KB LP SRAM. Clips live in flash (see Clips).
  • One 160 MHz RISC-V core plus a low-power core. Wi-Fi, TLS and effects share it, so effects render on a fixed frame budget and never block networking.
  • LEDC: 6 channels, 4 timers, so at most 4 distinct PWM frequencies. Hardware fades.
  • MCPWM: 6 more outputs, spare for PWM or motor drive.
  • RMT: 2 transmit channels, no DMA. Planned memory split: channel 0 gets 48 words, channel 1 gets 144 (borrowing the receive channels' blocks). The interrupt handler must be IRAM-safe. Fallback: SPI2 with GDMA.
  • Pins: 23 GPIOs on the module, about 17 free after USB (12/13), UART0 (16/17) and strapping pins (8, 9, 15). The GPIO matrix lets strip pins switch peripheral without a board change.

Board decisions

  • One board, populated per install. Some units carry every channel, some only one.
  • 6 PWM/switch channels on low-side MOSFETs, each with an optional flyback diode footprint.
  • 2 ARGB outputs with level shifting. Strip frame rate is about 100 fps at 300 LEDs and 33 fps at 1000; the two lines run in parallel.
  • One INA226 on the main input, ALERT wired to a GPIO for overcurrent. Per-channel current is estimated from calibrated profiles instead of measured.
  • Self-test without per-channel sensing: bring-up toggles each channel and checks the change in total current on the INA226.
  • A hardware revision ID so firmware knows which board it's on.
  • Under consideration TMC2209 stepper header (curtains), status pixel as pixel 0 of a strip, 4-layer stackup.

Component rules
  • main stays tiny. It starts the core and the services in order and contains no feature logic or #ifdefs. Adding or removing a component never touches it.
  • Every component has the same shape: CMakeLists.txt, a Kconfig with an enable switch and its options, a public header in include/, private code in src/, and tests in test/.
  • Dependencies point at the core. Drivers implement the core's channel interface (set, fade, read, safe state) and register what's fitted. Services talk to outputs through the core. MQTT never knows about LEDC, and the PWM driver never knows about MQTT.
  • Logic that can run off-chip is tested off-chip. Effect math, the contract encoder and state handling are plain C and run as host unit tests on the build machine.
  • Prefix everything ul_ so our components never clash with ESP-IDF or managed components.

05 · Real-time

Real-time control

v5 made sliders work by throttling twice: the browser sent at most every 100 ms, then the server queued commands and released one per node every 200 ms. The node ran a software smoothing task to hide the steps. The new path keeps the throttling idea but lets the LEDC hardware hide the steps instead. Each update fades over exactly the gap until the next update, so movement looks continuous.

Browser input events0
Messages to the node0
Saved as final state0

Try 5 Hz with "jump" to see the stepping v5 had to smooth out in software, then switch on the fade. When you let go, one final message is sent on the retained set topic so the value survives a reconnect.

The rules for anything that streams
  1. The browser sends on the leading edge, then at most every 50 ms, and always sends the last value on release.
  2. The server keeps the latest value per device and output, not per device. In v5 the queue was keyed by node only, so a command for one output could be overwritten by a command for another output on the same node.
  3. Live values go on live/{out} at QoS 0. The final value goes on set/{out}, retained at QoS 1.
  4. The node starts a hardware fade toward each value lasting one update interval. For ARGB, the renderer blends toward the new level over the same time.
  5. Other open browsers see the change through the reported state, so two people dragging at once both see what the light is really doing.
06 · Effects

Effects

v5 compiled 11 ARGB effects, 4 white effects and 3 RGB effects into firmware, each with its own parameters. Most went unused. The new design takes the approach WLED and FastLED users settled on: a few building blocks that all take the same parameters, with a palette doing most of the work.

Tier 1 · most use

Building blocks

About 10 renderers in firmware. An "effect" is a small JSON document choosing one, plus palette and parameters. You can download, edit and share effects without touching firmware.

Tier 2 · loops

Clips

Prerendered looping animations stored in a flash partition and replayed. Good for anything the building blocks can't express, including AI-made effects.

Tier 3 · reactive

Live frames

Frames rendered elsewhere (OpenRGB, screen or music sync) and streamed over the LAN. Only for content that reacts to something in the moment.

Effects lab

This is a simulation of the building blocks on a 72-pixel strip, with the glow it would throw on a wall. Every block takes the same parameters. The JSON on the right is the whole effect document a node would receive.

Scale means "how big the pattern features are". Intensity means "how strong the effect is" (depth of breathing, twinkle density, flicker amount). A random seed lets several strips show the same randomness in sync.

Clips and streaming

You asked whether a looping effect can be streamed once and replayed. Yes. The C6 has no PSRAM, so clips go in a flash partition. Writing a clip once and replaying it is fine for flash wear. Palette indexing (1 byte per pixel against a 256-color palette) usually cuts size by two thirds or more.

Clip size
Compared to all SRAM (512 KB)
Clips that fit a 4 MB partition
Share of the partition per clip

Before compression. Frames that change slowly compress much further with frame-to-frame differences. The player reads from flash a frame at a time, so a clip never has to fit in RAM.

Live frames how tier 3 stays fast

Routing 30 frames a second through the VM's MQTT broker adds latency and load for no benefit. Live frames go directly from the source (say the OpenRGB PC) to the node across the home LAN, using DDP over UDP. WLED and xLights use the same protocol, so existing tools work.

The server stays in charge: it opens a streaming session, gives both sides a short-lived session key, and the node drops frames that don't carry it. When the session ends or goes quiet, the node returns to its previous scene.

How grants work

  • Scope: whole home, rooms or single devices.
  • Abilities: view, control (on/off and level), color and effects.

  • Guests join through a single-use invite link and can't see anything outside their grant, including other rooms' names.
  • The AI acts as the person asking, so a guest's request can only touch what the guest can touch.

Fabrication bring-up

You plug a freshly assembled board into the computer running the admin panel, open Bring-up, and press one button. Flashing happens in the browser over Web Serial (Espressif's esptool-js, Chrome and Edge only), so no terminal is needed.

  1. Flash the factory image for the chosen board profile over USB.
  2. Self-test: walk each PWM channel, pulse each relay, run the ARGB line, read the temperature sensor and the hardware revision ID. With test points or current sense on the PCB, every result is measured rather than eyeballed.
  3. Create identity: the chip generates its private key, the server signs its certificate, and the board gets a serial number.
  4. Lock down (production boards only): enable secure boot and flash encryption. This burns eFuses and can't be undone, so the page asks you to confirm.
  5. Flash the release image and print a QR label with the serial and claim code.

Every step's result is stored against the serial. A board that fails any step is marked and never offered for claiming.

10 · Identity

Provisioning and certificates

v5 issued a certificate when the setup portal first exchanged credentials, so the server created the key. In the new flow the key is created inside the chip at bring-up and never leaves it. Claiming a device into a home is a separate, later step.

sequenceDiagram
  autonumber
  participant J as Admin bring-up page
  participant D as C6 node
  participant S as Server and CA
  participant O as Owner phone
  J->>D: Flash factory image over USB
  D->>D: Self-test, then generate key in chip
  D->>J: Test report and signing request
  J->>S: Submit report and request
  S->>J: Signed device certificate and serial
  J->>D: Store certificate, flash release image
  Note over J,D: QR label printed with serial and claim code
  O->>S: Scan QR to claim into a home
  O->>D: Wi-Fi details through the setup portal
  D->>S: Connect to MQTT with mutual TLS
  S->>D: Desired state and settings

The certificate name is the device ID, which the broker uses as the username. A device can't pretend to be another one, and a stolen certificate is revoked from the Certificates page.

Key handling CA layout and lifetimes
  • Root CA: kept offline (USB stick or password manager). Used only to sign intermediates.
  • Device intermediate: on the VM. Signs device and bridge certificates.
  • Firmware signing key: on the workstation, used by the build worker. Secure boot only accepts images it signed.
  • Lifetimes: long-lived device certificates (years), with renewal over MQTT before expiry, so a node that's offline for months still reconnects.
  • Wi-Fi setup: the setup portal (soft access point) works on every phone. BLE setup is nicer but Web Bluetooth doesn't work on iPhones, so the portal stays as the baseline.
11 · Delivery

Builds and OTA

Firmware is built per board profile, not per device. The admin panel queues a build, the workstation builds and signs it, and a staged rollout delivers it.

flowchart LR
  A[New release or profile change] --> B[Build job queued]
  B --> C[Build worker on workstation]
  C --> D[Signed image in artifact store]
  D --> E[Canary devices]
  E -->|healthy for 24 h| F[All devices on that profile]
  E -->|fails health check| G[Roll back and pause]
  • Every artifact records its ESP-IDF version, commit and profile, so any build can be reproduced.
  • A new image marks itself good only after it reaches the broker. If it can't, the bootloader rolls back on the next reboot.
  • The OTA command is never retained, and success is reported only after the broker acknowledges it. v5 learned both the hard way.
  • Owners see "Update available" and can approve it. You can push to anyone.
12 · Support

Problem reports

A report should take one sentence from the user. Everything else is collected automatically so you don't have to ask follow-up questions.

  • Who sent it, their role and home, the page they were on, app version and browser.
  • If sent from a device screen: firmware, signal, uptime, reset reason and the device's last 50 events.
  • An optional screenshot or photo.
  • A checkbox to leave the diagnostics out.

In the admin panel each report has a status (new, looking, fixed, won't fix), links to the device and the audit log around that time, and a reply the user sees under Help. If you want, new reports can also send you a push notification or email.

13 · AI

AI integration

The AI worker on the 4080 is a plugin, not part of the core. The core only needs four things from day one to make adding it easy later.

1. One command API

The model's tools are the same validated operations the UI uses: list rooms and devices, set state, create a scene, create a schedule. It can't do anything a person couldn't do by tapping.

2. Scenes and effects are data

"Make the living room space vibes" produces a scene document: a flow effect, a deep blue and purple palette, slow, 30% brightness. It can be previewed, saved, edited or undone.

3. Every change has a source

Changes are tagged ai:<user> in the activity log, and "undo last AI change" is one tap.

4. Room layout in the data model

Each light can have a position, and each strip a path and pixel count. Unused at first, it's what makes image-to-scene possible later.

Image to scene

The simplest layout model that works treats each room like a picture frame. The owner places each light on a frame of the room, the way ambient-TV tools place LEDs around a screen. Matching an image is then a matter of sampling the image at those positions. A vision model chooses the overall mood and palette, and the sampling decides which color goes where.

The images are generated stand-ins for a user's screenshot. Dashed lines are strips, circles are lamps, and the rows below are the colors each fixture would receive.

Request flow text request to lights
  1. The user types or says a request. The API stores it as a job tagged with the user's identity.
  2. The AI worker claims the job and calls read-only tools to see the rooms, devices and capabilities this user can access.
  3. It proposes a scene document. The server validates it against the contract and the user's grants.
  4. It is applied right away with an Undo button, or shown as a preview card, depending on a user setting.
  5. If the workstation is off, the request waits with a "thinking" status or times out politely.
14 · History

Lessons from v5

Each lesson below was checked against the v5 code or commit history and re-judged for the C6, ESP-IDF 6.x and the new design. Anything that only made sense given v5's constraints is marked as dropped, so it doesn't creep back in.

Rework Live sliders need throttling at both ends

Evidence: browser throttle at 100 ms in Server/app/templates/modules/white.html (scheduleSend); server queue at 5 Hz per node in Server/app/mqtt_bus.py.

Keep: leading-edge send, latest value wins, final value always sent.

Change: the server queue keeps one pending command per node, so a command for one output can silently replace another output's. Key it by device and output. Raise the rate to about 20 Hz and let hardware fades cover the gaps. See Real-time control.

Keep State is retained, commands are not

Evidence: commit "Avoid retaining OTA command"; mqtt_bus.py retains light state so lights resume after reconnecting.

New form: separate set/ (retained) from cmd (never retained) in the topic layout itself, so it can't be gotten wrong per call.

Keep OTA needs large partitions, acknowledged reporting and relative URLs

Evidence: commits "Ensure default sdkconfig uses two large OTA partitions", "Ensure OTA success publishes wait for MQTT ack", "Resolve OTA binary URLs relative to manifest", and a reverted attempt at namespaced paths.

New form: 8–16 MB flash with the partition table designed up front; artifacts addressed by content hash; rollback built in.

Keep Every MQTT client needs a unique, stable ID

Evidence: commit "Throttle node commands and fix MQTT client IDs".

New form: the client ID, certificate name and device ID are the same string, so they can't collide.

Keep Newer chips have no LEDC high-speed mode

Evidence: commit "Handle LEDC speed mode absence on newer targets". The C6 only has low-speed mode, so the new driver uses it from the start.

Drop Software smoothing tasks on the node

Evidence: the white engine ran a periodic smoothing task (CONFIG_UL_WHITE_SMOOTH_HZ) with its own failure handling. LEDC hardware fades replace it entirely.

Drop A large compiled-in effect catalog

Evidence: 11 ARGB effects in ul_ws_engine/effects_ws, plus separate white and RGB effect sets, each with its own parameter list. Replaced by building blocks and palettes. Some old looks (fire, space waves, triple wave) are worth recreating as effect documents to test the building blocks.

Drop JSON files as the database; per-node config files

Evidence: device_registry.json, motion_prefs.json, custom_presets.json, brightness_curve.json and others in Server/app; 37 files in UltraNodeV5/node_configs. Replaced by one database and a few board profiles.

Rework Time-of-day brightness curve

Evidence: brightness_curve.json stored hourly brightness points per room and channel. It's a useful idea but was its own subsystem. In the new design it becomes a kind of schedule: "follow this curve" (with warmth too, for a circadian feel).

Rework Motion sensing

Evidence: ul_pir component, an ultrasonic sensor using RMT, and server-side motion schedules with retained "off" commands. Whether sensors are in scope is an open question. If they are, they'd be inputs in the device contract feeding the scheduler, not special cases.

Process Write the spec before the code

Evidence: about 370 pull requests, including repeated reverts of the same feature (four reverts of "glowing border buttons" alone) and dozens of leftover branches. Agents writing code against an unwritten spec produced churn.

New form: this document and the contract schemas come first. Work goes in small end-to-end slices with acceptance checks.
